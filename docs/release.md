# Релиз локального приложения

Этот файл описывает выпуск версии для разработчика, а не действие пользователя.
Пользователь скачивает готовый комплект из GitHub Release и запускает его одной командой.
Пайплайн публикации описан в [`.github/workflows/release.yml`](../.github/workflows/release.yml).

## Что публикует релиз

- versioned multi-architecture образ `ghcr.io/slavaklkv/ai-operations-agent` для
  `linux/amd64` и `linux/arm64`, с тегами `<версия>`, `v<версия>` и `latest`;
- встроенные OCI-attestations SBOM и provenance — по релизу видно, из чего и из какого
  commit собран образ;
- keyless-подпись образа через OIDC, без долгоживущих секретов;
- комплект пользователя `ai-operations-agent-<версия>.tar.gz` и `.zip` с `compose.yaml`,
  стартовыми и сервисными скриптами, README и LICENSE;
- `SHA256SUMS.txt` с контрольными суммами распространяемых архивов.

В `compose.yaml` внутри комплекта версия образа закреплена под конкретный релиз. Файл в
repository хранит текущую версию разработки — их совпадение проверяет
`tests/delivery/test_user_bundle.py` и шаг резолвинга версии в самом пайплайне.

## Порядок выпуска

1. Убедиться, что `develop` зелёный и содержит все изменения релиза.
2. Поднять версию в `pyproject.toml`; при необходимости `uv lock`, чтобы lock-файл совпадал.
3. Проверить, что базовый образ и зависимости зафиксированы, а `make check` проходит.
4. Закоммитить изменение версии в `develop` и дождаться зелёного CI.
5. Поставить тег `v<версия>` на этот commit и запушить его. Тег запускает `Release`.
6. Для повторного выпуска без push тега доступен ручной запуск `workflow_dispatch`
   с указанием версии; он привязывает тег к собранному commit.

Версия тега обязана совпадать с `version` в `pyproject.toml` — иначе пайплайн прерывается
до публикации образа.

## Проверка после публикации

Проверять нужно на релизных артефактах, а не на дереве разработки:

```bash
# 1. Комплект распакован рядом с каталогом, где запускаются команды.
shasum -a 256 -c SHA256SUMS.txt        # или: sha256sum -c SHA256SUMS.txt
tar -xzf ai-operations-agent-<версия>.tar.gz
cd ai-operations-agent-<версия>

# 2. Один сервис, порт только на loopback, валидная конфигурация.
docker compose -f compose.yaml config | grep -E '127\.0\.0\.1|published'

# 3. Образ тянется и приложение поднимается здоровым.
./start.sh
curl -fsS http://127.0.0.1:8000/health
```

Для подписанного образа дополнительно проверяется автор подписи:

```bash
cosign verify ghcr.io/slavaklkv/ai-operations-agent:<версия> \
  --certificate-identity-regexp 'https://github.com/SlavaKlkv/ai_operations_agent/.*' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com
```

## Обновление и сохранность данных

- Остановка и обновление сохраняют volume с SQLite и runbook;
- если локальная база отстала от head, перед применением миграций автоматически
  снимается согласованная копия `<база>.pre-upgrade.bak` и логируются ревизии от→до,
  поэтому состояние до обновления всегда восстановимо;
- перед рискованным обновлением дополнительно выполняется проверяемый backup:
  `./manage.sh backup <файл.db>`, восстановление — `./manage.sh restore <файл.db>`;
- миграции применяются при старте контейнера; необратимые миграции описываются в
  release notes вместе с путём отката;
- удаление данных требует явного `./manage.sh destroy --delete-data` и не выполняется
  командами остановки или обновления;
- резервная копия одной SQLite не переносит авторизацию GitHub: ключ и зашифрованный
  токен лежат отдельными файлами рядом с базой (см. [документацию GitHub App](github-app.md)).

## Диагностика

Для обращения в поддержку соберите отчёт без секретов:

```bash
./manage.sh report agent-report.json
```

Отчёт содержит безопасные поля конфигурации и состояния. Токены, пароли и учётные
данные внутри строк подключения маскируются ещё до записи на диск, поэтому файл можно
приложить к обращению. Код маскирования и его тесты — в
`app/observability/diagnostics.py` и `tests/observability/test_diagnostics.py`.

## Откат

Откат выполняется на предыдущий versioned образ, а не на `latest`:

```bash
AOA_IMAGE=ghcr.io/slavaklkv/ai-operations-agent:<предыдущая-версия> ./manage.sh update
```

Если новая версия изменила формат данных необратимо, перед откатом восстанавливается
backup, снятый на предыдущей версии. `manage.sh restore` сохраняет вытеснённую базу как
`ai_operations_agent.db.before-restore`, поэтому ошибочное восстановление обратимо.
